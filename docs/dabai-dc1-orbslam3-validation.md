# Dabai DC1 办公室 ORB-SLAM3 离线验证

日期：2026-09-13。结论：算法能初始化并跟踪部分场景，但这两段办公室实录均未通过连续定位筛查；不能据此作为可靠的单独导航定位源。主要问题是反复失跟、新建地图及地图修正导致的原始位姿不连续，当前主机核心处理速度不是首要瓶颈。

## 实验范围与输入

在指定 worktree 中读取真实 DC1 bag，使用现有镜像内的 ORB-SLAM3 C++ 核心、RGB-D 模式离线运行。没有使用占位 ROS bridge；它只发布 BLOCKED 诊断，没有算法调用。没有机器人动作或实时导航接入。

- `office-20260913-212016`：1292 RGB / 1397 深度，约 46.5 秒，RGB 27.77 Hz。唯一最近邻配对保留 1275 对，排除 17 个 RGB；保留配对时间差 p95 15.92 ms。
- `office-20260913-212121`：753 RGB / 980 深度，约 32.6 秒，RGB 23.06 Hz。保留 740 对，排除 13 个 RGB；保留配对时间差 p95 16.45 ms。
- 最大允许配对差 30 ms，不重复使用深度帧；该离线最近邻规则使用未来帧，实际在线同步需要等待并增加延迟。统计通过不表示曝光硬同步。
- RGB 640×480、深度 640×400。实验采用 RGB 顶部 400 行，深度原样保留；没有拉伸深度或强行中心裁剪。依据是两路 CameraInfo 的相同 K、参考驱动点云分支的顶部裁剪逻辑以及代表帧边缘叠加。几何精度未经标定板验证，这一假设仍可能影响精度。
- 内参 fx=fy=488.090332、cx=320.885315、cy=211.704376；畸变采用消息中的零值；16UC1 按驱动已验证的毫米单位设置 factor=1000。PNG 读取为 BGR，设置 Camera.RGB=0。Stereo.b=0.075 与 ThDepth=40 仅用于设置 3 m 近点阈值，不是本次测得的物理基线。

## 结果

有效跟踪严格使用每帧 `GetTrackingState()==2`，分母是实际输入配对帧；不是用最终轨迹行数推算。

| bag 尾号 | 配置 | OK 帧 / 输入 | 新建地图事件 / 合并事件 | 核心耗时 p95 | 相邻 OK 原始位姿最大变化 |
|---|---|---|---|---|---|
| 212016 | baseline | 836/1275 (65.57%) | 6 / 1 | 11.44 ms | 2.172 m |
| 212016 | features2000 | 829/1275 (65.02%) | 6 / 1 | 17.94 ms | 0.975 m |
| 212016 | repeat | 830/1275 (65.10%) | 6 / 0 | 12.04 ms | 0.265 m |
| 212121 | baseline | 650/740 (87.84%) | 2 / 1 | 12.86 ms | 1.144 m |
| 212121 | features2000 | 650/740 (87.84%) | 2 / 1 | 18.18 ms | 1.227 m |

初始建图计入“新建地图事件”；这是事件数量，不是最终保留下来的地图数量。两份 baseline 的 OK 帧占原始全部 RGB 比例分别为 64.71% 与 86.32%。全部 5 次运行完整处理输入并正常退出；实验未崩溃不等于连续定位通过。

1000 特征的第一段复跑再次产生 6 次建图，OK 65.10%，失跟结论可复现；合并事件从 1 变成 0，说明多线程执行的地图合并结果并不完全确定。2000 特征没有改善两段跟踪覆盖率，p95 升至约 18 ms，不建议把增加特征数作为此问题的修复。

## 失败段与容易误判的问题

1. **画面退化与失跟重合。** 第一段 baseline 在 16.932–19.976、24.120–27.128、28.300–31.308、35.756–38.764、42.920–45.920 秒非 OK；第二段为 20.344–23.400、30.968–32.604 秒。抽帧显示快速转动的模糊、白墙/天花板低纹理，以及重复窗帘纹理。OK/非 OK 帧的 Laplacian 方差中位数分别约 112/30、95/40；这是相关证据，不能单独证明模糊是唯一原因，纹理量本身也会影响该指标。
2. **约 3 秒是算法状态机，不是 bag 断流。** RGB-D 的 RECENTLY_LOST 分支在重定位超过 3 秒未成功后转 LOST，再新建地图。实际输入最大间隔约 84 ms。后续重新 OK 可能只是另一张地图的初始化，不代表回到了原地图。
3. **OK 状态也可能伴随坐标修正。** 第一段 23.084→23.116 秒的原始输出变化约 2.172 m；第二段 25.856→25.892 秒约 1.144 m。对应日志时段存在 Merge 和 Change to map；推断变化包含地图坐标系修正，不能解释为真实移动速度或直接称为同一坐标系内的漂移。当前记录未给每帧附 atlas map ID，不能精确归因每次变化。即使如此，它们也不能直接作为要求连续的 odom 输出。
4. **导出轨迹可能掩盖失败与多地图问题。** 上游 SaveTrajectoryTUM 会跳过被标记丢失的帧，且不会给每行标地图 ID。必须联合 tracking.csv、run.log 查看；state!=2 的原始 CSV 位姿不应使用。不要把不同局部地图拼成一条路径计算里程或起终点误差。本实验日志记录了地图合并，未记录同地图 Loop 事件或 Relocalized!! 成功事件；合并不能等同于全程连续跟踪。
5. **性能与精度结论有边界。** CPU 为 Core Ultra 7 255H；viewer=false、OpenCV 线程数 1，核心基线 p95 11.44/12.86 ms。计时只覆盖 TrackRGBD，不含图像读取、ROS 传输、同步等待或实际相机曝光延迟，不能外推为目标板端实时性能。按原时间间隔做近似节奏回放，读图额外开销让整体比实录慢；没有硬实时丢帧压力测试。没有外部真值/已知闭合运动，也没有几何标定板，因此没有声称 ATE、RPE 或厘米精度。

## 建议的下一步

先把 RGB/深度几何和时间同步标定明确，再补录“相机水平、缓慢平移转动、纹理物体始终入镜、回到标记起点”的对照 bag，并单独录白墙和快速转动退化段。验证恢复时应记录 map ID 与地图修正事件，并隔离 map 校正与连续 odom；不能仅用 OK 状态决定恢复导航。若需要跨低纹理/快速转动持续定位，应另验证带可用 IMU 或轮速/其他定位源的融合方案；本次 bag 没有验证这些能力。

## 可复现入口与证据

在该 worktree 运行（必须使用新的实验目录名，原始 bag 只读）：

```bash
bash scripts/orbslam3-validation/run.sh orbslam3-validation-rerun-01
```

脚本重放两段的 baseline 与 features2000，汇总后执行连续性筛查。本次筛查标准是完整处理、OK≥95%、不新建第二张地图、相邻 OK 原始位姿变化≤0.5 m；这是显式的实验筛查标准，不是行业验收标准。预期本数据返回 FAIL/退出码 1；命令运行错误与筛查失败需要区分。第一段额外 baseline repeat 的实际结果也已保存。

原始逐帧数据、完整日志、TUM 导出、诊断图、失效抽帧和运行汇总都在：
`artifacts/perception-dev/dabai-dc1/orbslam3-validation/`。

- `summary.json`：所有已完成实验的统计与失败区间。
- `manifest.json`：镜像 ID、CPU、源版本声明与脚本/metadata 哈希；并非原 bag 内容的完整校验和。
- `<bag>/<run>/tracking.csv`、`run.log`、`CameraTrajectory.txt`、`KeyFrameTrajectory.txt`、`diagnostics.png`。
- `<bag>/failure-samples.jpg`：基线失跟起点及最大原始位姿变化附近的实际画面。
- `<bag>/samples.jpg`：代表帧与深度边缘叠加；`input.json`：配对与图像质量记录。

保留了约 795 MB 的可复用无损抽帧与证据；原 bag、已有录制节点和正式 ROS bridge 未修改。本次仅新增离线实验工具与报告。
