# Kuruma Fortress simulation

`ros2 launch soarm_simulation simulation.launch.py` starts the native Fortress `kuruma` model and ROS compatibility adapter. Kuruma is a four-wheel holonomic mecanum chassis: `/cmd_vel` carries `linear.x`, `linear.y`, and `angular.z` through a 0.5 s fail-safe timeout to Fortress `ignition::gazebo::systems::MecanumDrive` on `/safe_cmd_vel`. The configured roller-envelope radius is `0.0763 m`, wheelbase `0.3472 m`, track `0.4456 m`, and the collision-relevant frame perimeter is `0.600 m` square.

Fortress 6 `MecanumDrive` accepts wheel velocity commands but its bundled official example does not emit encoder odometry. Kuruma integrates the four `/joint_states` wheel positions into `/odom` and the `odom_combined -> base_footprint` TF, so contact slip remains visible to localization consumers. Fortress's native `OdometryPublisher` separately publishes physical model state on `/gazebo/odom`; the adapter exposes that state as `/ground_truth/odom` for scoring only. Camera, chassis IMU, MID-360 point cloud, and LiDAR IMU topic/TF seams remain available through provisional mounts. They are compatibility geometry, not STEP-derived extrinsics or hardware sensor validation. The simulated Livox output remains an algorithm-compatibility approximation, not a physical MID-360 timing or optical model.

This is a chassis-first stage. The default URDF and SDF contain no arm geometry or active arm controller. `/arm_controller/follow_joint_trajectory`, `/gripper_controller/follow_joint_trajectory`, and `/go_to_place_and_grasp` remain discoverable only to fail closed: with `arm_enabled=false`, every goal is rejected and no grasp or mission success is fabricated. Arm mounting dimensions and position are the next mechanical study.

`world:=navigation_room` and `world:=house_floorplan` include the same native `kuruma` model. The prior WHEELTEC chassis state is retained at `backup/wheeltec-chassis`.
